# DevKit

Many of the tools developers keep reaching for, in one place.
*Ad-free and cookie-free.*

## Self hosting

Go ahead, put it on your own domain or subdomain for your private use.

Many of the tools also work online if you just drop it in a folder.

## Public version

There is a public version with the tools that don't use server CPU (no PHP
or similar) for people who don't want to, or can't, host their own clone of
the toolkit.

## Why

I used to rely on a lot of good online tools that made my life easier, but
over time they were getting annoying.

- Each one its own style
- Accept cookies
- Put up with ads

So I decided to build my own toolkit. *Ad-free and cookie-free.*

## How it works

Each tool is an `HTML` file with its `JS`, its `CSS` and, optionally, a `PHP`
backend. They are all registered in `registry.json`. `index.html` reads that
registry, renders the menu and loads each tool's files on demand when you
open it.

Fields of a `registry.json` entry:

| Field | Use |
|---|---|
| `name`, `title`, `description`, `howto` | menu and header text |
| `slug` | route (`/base64`), must start with `/` |
| `html`, `css`, `js` | the tool's files |
| `php` | optional backend |
| `needs` | array of runtime dependencies, e.g. `["php"]`. No `needs` = static |
| `private` | personal tool: excluded from every published build |
| `assets` | extra files to copy (on top of local `import`s, which are detected automatically) |

## Development

No dependencies. Node is only needed for `build.js` / `test.js`.

```sh
# serve the tree as-is (the PHP tools need a server with PHP)
php -S localhost:8000
#   or any static server if you're not touching the PHP tools:
python -m http.server 8000
```

`index.html` derives its base URL from the page location, so it works the
same at a domain root, in a subfolder or on `localhost` with no config.

When you add or change a tool, regenerate the [Tools](#tools) section (it is
filled automatically from `registry.json`):

```sh
npm run readme
```

Validate the registry and check the README list is in sync:

```sh
npm test
```

CI runs both checks on every push and PR.

## Build

`build.js` produces a deploy-ready copy, with no dependencies.

```sh
# public edition: drops tools with a "needs" and the "private" ones
node build.js --target=public --base=https://devkit.albin.es/ --out=dist

# full edition: drops only the "private" ones
node build.js --target=full --out=dist-full
```

With `--target=public` it also removes any `.php`, regenerates `sitemap.xml`
and `robots.txt` with the `--base` domain, and stamps the service worker
cache name.

## Editions

| Where | Command | Includes |
|---|---|---|
| Your working clone | -- | everything, including `private` |
| Self-host with PHP | release `.zip` (`--target=full`) | everything except `private` |
| Self-host without PHP | `--target=public` | static tools only |
| `devkit.albin.es` | `--target=public` (CI) | static tools only |

## Deploy

The public site deploys itself: every push to `main` triggers
`.github/workflows/deploy.yml`, which runs `build --target=public` and
syncs `dist/` to the server over `rsync`/SSH.

It is disarmed until you set the repo variable `DEPLOY_ENABLED=true` and
these values in *Settings > Secrets and variables > Actions*:

- Variables: `PUBLIC_BASE` (`https://devkit.albin.es/`), `SSH_PORT` (optional)
- Secrets: `SSH_HOST`, `SSH_USER`, `SSH_KEY`, `SSH_KNOWN_HOSTS`, `DEPLOY_PATH`

Equivalent manual deploy:

```sh
DEPLOY_TARGET="user@host:/path/to/webroot" npm run deploy
```

A `vX.Y.Z` tag publishes a release with the `.zip` of the full edition
(`.github/workflows/release.yml`).
